# Video-Handoff über URL-Param + IndexedDB, kein globaler State-Store

Das in `/editor` hochgeladene Video-File muss `/player` erreichen, auch nach einem Reload oder direktem Link-Aufruf auf `/player`. Wir speichern den Video-Blob direkt in **IndexedDB** (Key: generierte `videoId`, plus Metadaten wie Name/Typ/Uploaddatum), reichen nur die **`videoId` als URL-Param** (`/player/:videoId`) zwischen den Routen weiter, und lassen `/player` den Blob per ID nachladen sowie sich seine `URL.createObjectURL()` frisch selbst erzeugen (revoked beim Unmount). Vor dem Schreiben in IndexedDB wird der Upload clientseitig auf Typ (MIME-Type) und eine Größenobergrenze (500 MB) geprüft (nur Best-Effort, kein hartes Security-Boundary — da es  keinen Server gibt, der das unabhängig verifizieren könnte).

Player-Controls (`currentTime`, `volume`, `isRecording`) bleiben lokaler Component-State in `/player` und werden nicht global oder in Context gehoben. Konsequenz: Ein Reload auf `/player` verliert die Abspielposition (Video startet wieder bei 0) — der Blob selbst bleibt aber erhalten, kein erneuter Upload nötig. Bewusst akzeptierter Trade-off für den 3-Tage-Rahmen, keine Fehlfunktion.

**Warum Typ-Prüfung beim Upload:** HTML5-`<video>`/Vidstack spielt zuverlässig nur bestimmte Container/Codecs (MP4/H.264, WebM/VP9). Ohne Einschränkung könnte eine Lehrkraft versehentlich eine falsche Datei (`.mkv`, `.zip`, o. Ä.) auswählen, die entweder gar nicht abspielt oder einen leeren/kaputten Player zeigt — die Prüfung ist also primär ein **UX-/Funktionalitäts-Guard** (klare Fehlermeldung sofort beim Upload statt stiller Fehlschlag im Player), erst sekundär Security. Wichtig zu benennen: `file.type` wird vom Client gemeldet und ist **nicht vertrauenswürdig** (umbenennbar/spoofbar) — ohne Server, der das unabhängig verifizieren könnte, bleibt das der Best-Effort. Ein zusätzlicher Magic-Bytes-Check (Datei-Header auf bekannte Video-Signaturen prüfen, statt nur `file.type`) wäre eine robustere, aber optionale Erweiterung, falls Zeit bleibt.

**Warum eine Größenobergrenze (500 MB):** IndexedDB-Quota ist endlich und pro Origin geteilt; auf schwacher Schul-Hardware (Chromebooks, alte Laptops mit wenig freiem Speicher — s. ADR-0002) kann ein unbegrenzter Upload die Quota sprengen (`QuotaExceededError` mitten im Schreibvorgang) oder den Tab bei Dekodierung/Pufferung einfrieren. Eine Obergrenze hält Ladezeit und Ressourcenverbrauch in einem für Zielgeräte vorhersehbaren Rahmen (Performance-Kriterium der Aufgabe) und ist eine einfache Konstante, die sich leicht anpassen lässt.

**Sicherheitseinordnung (kurz):** Beide Prüfungen sind clientseitig und damit umgehbar (z. B. über DevTools direkt in IndexedDB schreiben) — sie sind kein hartes Security-Boundary, sondern reduzieren Fehlbedienung und Ressourcen-Erschöpfung für den normalen Nutzungsweg über die UI. Die eigentliche Sicherheitsgarantie gegen Code-Ausführung kommt nicht von unserer Validierung, sondern daraus, dass Videodateien vom Browser als Mediendaten dekodiert und nicht als Code interpretiert werden.

**Warum URL-Param statt global State-Store — der Unterschied konkret:**

Mit einem State-Store (Zustand/Jotai) würde `/editor` die ID in den Store schreiben (`useVideoStore.setState({ activeVideoId: "abc123" })`), und `/player` sie per Hook wieder auslesen. Das funktioniert *nur solange die Seite nicht neu geladen wird* — bei einem Reload ist der komplette JS-Speicher weg, der Store startet leer, `activeVideoId` ist `undefined`. Man bräuchte zusätzlich Persistenz-Middleware (z. B. Zustand `persist` → localStorage), um das aufzufangen: mehr Code, mehr Abhängigkeiten, für ein Problem, das die URL von Haus aus löst.

Mit dem URL-Param (`/player/:videoId`) navigiert `/editor` direkt zu `navigate(`/player/${videoId}`)`, und `/player` liest die ID per `useParams()` — direkt aus der Adresszeile, die React Router ohnehin schon parst. Die ID steht jetzt buchstäblich in der Browser-Adressleiste (`/player/abc123`). Ein Reload lädt einfach dieselbe URL neu, `useParams()` liefert die ID sofort wieder — **kein Store, kein Provider, keine zusätzliche Library, kein eigener Persistenz-Code.** "Robuster" heißt hier konkret: überlebt Reload gratis, weil die URL selbst schon der Speicherort ist — plus sie ist teilbar/bookmarkable, ein Store-Wert nie.

**Considered:**
- **Zustand / Jotai** — verworfen aus obigem Grund: der einzige routenübergreifende State ist eine einzelne ID, ein Store wäre zusätzliche Maschinerie (inkl. eigener Reload-Persistenz) für ein Problem, das die URL bereits löst.
- **React Context** für die Video-ID — verworfen aus demselben Grund, plus: Context re-rendert bei jeder Änderung alle Consumer im Baum. Wäre für Player-Controls wie `currentTime` (ändert sich pro Frame) ein konkretes Performance-Risiko auf schwacher Schul-Hardware — deshalb bleiben Controls bewusst lokal statt global/Context.
- **Nur In-Memory Object-URL ohne IndexedDB** — verworfen: überlebt keinen Reload/direkten Link-Aufruf auf `/player`, da Blob-URLs beim Entladen des erzeugenden Dokuments ungültig werden (s. ADR-0002).

**Consequence:** `/player` funktioniert robust auch bei Reload oder direktem Linkaufruf, und Video- sowie Recording-Daten teilen sich eine Persistenzschicht (IndexedDB). Kehrseite: keine Verschlüsselung-at-rest und keine Auth (folgt aus ADR-0001) — auf einem geteilten Schulrechner/Browserprofil kann jede Person mit Zugriff auf denselben Browser gespeicherte Videos/Aufnahmen einsehen. Das ist eine bewusste, dokumentierte Grenze des No-Backend-Ansatzes, kein Versehen.
